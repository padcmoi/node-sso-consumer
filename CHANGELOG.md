# CHANGELOG

## [Unreleased] - 2026-08-22

- Add `poc/nuxt4-nest`, where the library runs in a NestJS API the browser never reaches, behind a Nitro relay - the architecture of `manager-infra` and of most of this house's projects, and the one this library had only ever DESCRIBED. `docs/nestjs.md` was prose: nothing had booted it, no test exercised it, and four of the applications waiting to be migrated are Nest. The front half is the proof: `plugins/sso.client.ts`, `composables/useSso.ts` and the pages are the same files as in `poc/nuxt4-nitro`, because the browser only ever talks to its own origin and cannot tell which side of the relay holds the session. What moves is the page guard - under Nitro the library refuses before a byte is written, and here it cannot, because it is not on that side at all, so the console asks over the same relay every other call goes through. Two things break silently in this shape and both are written down where they bite: the callback belongs to the FRONT's address because a browser walks it, and `trust proxy` is what makes a `Secure` cookie survive a relay that terminates TLS in front. It ships blank - no install token, `not-paired` in one line at boot, and nothing served behind the SSO
- Put `accept` back by hand in the POC's relay, because h3 DROPS IT: the header sits in h3's own `ignoredHeaders` beside `host` and `accept-encoding`, so `getProxyRequestHeaders` never returns it and an API behind a Nitro relay cannot see what the caller asked for. Content negotiation is not degraded there, it is impossible - every refusal took the browser branch, so an XHR on a guarded route was answered with a `302` towards the portal and a `fetch` that follows redirects handed the component the portal's HTML where it expected JSON. It is the exact failure the guides warn about, arriving from the one place nobody looks. Pair the POC against the real x-core to see it: it does not show until a refusal has a portal to name
- Pair `poc/nuxt4-nest` against the production x-core and keep the install token in the file, spent, as `poc/nuxt4-nitro` does. Proven end to end over `https://tvx-gp3.gestionpratique.ovh`: pairing, the twenty keys written into `app_settings` with a sealing password minted locally, the credential hash delivered on the broker queue within the second, a declaration that signs with it and passes on every later boot without re-pairing because `INSTALLED` short-circuits, the authorize redirect with its `Secure` state cookie, both branches of a refusal, a browser sign-in through the portal, and a realtime socket whose `4402` travels back through the reverse proxy and the relay untouched
- Point `exports` at the `.d.cts` declarations under the `require` condition, per subpath. One `types` served both, and since this package is `"type": "module"` TypeScript read that declaration as ESM - so every CommonJS consumer was refused with `TS1479` and could not import this library AT ALL. That is every NestJS project in this house, `nodenext` being what they resolve with, and four of the applications waiting to be migrated are Nest. The `.d.cts` files were built by `tsup` and shipped in the tarball the whole time; nothing pointed at them. Found by booting `docs/nestjs.md` for the first time
- Leave `live` at `false` in that POC rather than copying it on. It follows every account this process holds a session for and hands what arrives to `di.onAccount` and `di.onSignedOut`; neither is lent there, so every one of those sockets carries frames to nowhere - one against x-core per signed-in reader. The realtime a reader actually sees is the ticket bridge, which is untouched by it
- ASK THE PROVIDER ON EVERY READ. `SsoLiveAccounts` no longer answers a guard: it is a relay onto `di.onAccount` and `di.onSignedOut`, and `live.staleAfterMs` is gone with the ceiling it defined. A followed account was served for five minutes between proofs, on the reasoning that a socket which pushes every change cannot go stale - and there is exactly one change it cannot push. A session ended from the portal's sign-ins screen closes NOTHING over there: x-core re-checks a live socket against the IdP session and the account's access, deliberately not against the consumer session row, because that row is replaced at every rotation and pinning a socket to it would close every socket a quarter of an hour in. So the frame never came, and a reader whose session had been revoked kept every door of the consuming application open for five more minutes
- Take what an application REQUIRES from the provider's own answer, `permissions.portail`, and make the door one comparison: `global` holds every entry of `portail`, or the session is over here and the reader goes back to the portal. Both lists speak `resource:action`, so it is a subset test with nothing to parse, split or namespace - and an empty `portail` requires nothing and admits everybody, which is the common case. It was read from what the pairing wrote into the application's own store, and a store is a COPY: an operator adding a requirement on the console changed it over there while every consuming application went on admitting whoever it had admitted the day it was installed. Root needs no exception, being answered the whole catalogue in its `global`. A provider too old to answer the key demands nothing by saying nothing - the only place this parser forgives an absent field, because everywhere else the empty reading is the one that opens a gate
- Read a `403` on the identity read as the access revoked, not as an expiry: `resolve` answers `null` without rotating. Rotating asked the same question twice - the provider checks the access on that path too - and the only thing it bought was a later sign-out
- Put the sign-out on the instance, `xcore.logout(req, res)`, and make it ANSWER where the reader goes rather than redirect there: the portal when this application is paired, its own sign-in screen when the library is standing in. A `302` written into a `fetch` is a response nothing follows - the cookie was cleared and the reader stayed on a page that no longer had a session behind it, until they refreshed by hand. The browser half navigates to what came back
- Kill the realtime bridge while standing in. There is no provider holding that session, so nothing pushes to it: the ticket route answers `404`, which the browser half now tells apart from a `401` - the first means this deployment HAS no stream and the reader is signed in perfectly well, the second means the session is over. Collapsed into "no ticket", it signed everybody out on a deployment that simply has no socket, and the sign-out led back to a page that dialled again, forever
- Subscribe to `me-sessions`, the third always-on topic, and leave a page whose own sign-in disappears from it. That is the ONE way of ending a session `me-signed-out` cannot report: the provider computes it from the IdP session and the account's access, and ending one application's session from the sign-ins screen moves neither - so the frame never came and the page kept painting. Nothing had to be added anywhere: the topic exists, the provider already marks the caller's own line `current`, and this simply listens. Latched on first sight, because a socket with no line to match would read "none is mine" from its first frame and sign everybody out; and settled by ONE read of `/session`, because rotation replaces the row every fifteen minutes and a frame read in the gap shows no line of ours while the session is perfectly alive. This client polls NOTHING - the socket says when something ended, which is what a socket is for
- Refuse through ONE path, whatever the cause. Session over, x-core refusing, x-core unreachable, credential never delivered, never paired: in every one of them nothing was learned about the reader, so the answer cannot differ. To the portal - and `500` when there is no portal to send anybody to, which is an application that never paired, since that address arrives WITH the pairing. `FORBIDDEN` is the one that stays apart, and stays a `403` where the reader stands: the account IS signed in and simply lacks the right, so signing in again would change nothing and loop
- Answer the refusal in the guard rather than handing it to `errors()`. A refusal that depends on an error handler being mounted is one an application can forget to install, and forgetting it did not fail loudly - the request carried on into a framework's default page, which is not a refusal at all
- Throw `NOT_CONFIGURED` from `session()` instead of answering `null` when this library cannot reach the provider. The two are not the same thing and collapsing them was the whole defect: `null` means nobody is signed in, which a caller answers with a `401` and a way to sign in; this means there is no way to sign in at all. Read as the first, every caller said "not signed in" and served the shell of its application to anyone. `statusOf` is the library's own table for turning one into a status, so no application has to work out that a deployment nobody configured must not tell a reader to sign in
- Lend the library `di.errors(refusal, req, res)`. It decides WHETHER and WHY - it is the only thing that talks to the provider, so it is the only thing that can - and calls this from inside that decision to say HOW. The request and response travel with the refusal so one function answers every kind: a `302` written on the response where there is a portal, a throw where the framework stops a handler that way. Optional: lend nothing and the library writes the plain answer itself, and it never writes over a response the application already ended
- Add `account(req, res, ...actions)` for handlers that ASK rather than sit behind a middleware - Nitro, Fastify, a plain route table. The session and the actions are checked in one call and in that order, because two calls are two things to remember and the one that gets forgotten is the first, which is a route asserting rights against an account nobody read
- Default `routes.basePath` to `/api/auth`, not `/auth`. x-core's console COMPOSES the callback it records from the application's address, and it writes that path with no field offering another - so an application configuring nothing was declared at one address and listened at another. It showed up at the first sign-in, as a callback that does not match, on a row whose host is pinned and cannot be edited. Every example in this repository already overrode the old default: a default no document uses is a trap for whoever trusts it
- Drop frames from the page that will not parse, instead of forwarding them. An `auth` frame was already refused - the account behind a socket is decided by the ticket that opened it - and anything unreadable now goes the same way: forwarded, it is a byte string this end never looked at, arriving at the provider over a connection that vouches for this application

- Stop saying that x-core revokes the manager key when a pairing code is spent. It did, and it does not any more: one key installs as many applications as an operator has to install, so it is theirs to keep and theirs to revoke over there. Nothing in this library changes - the pairing answer, the routes and the store keys are untouched - but four documents described a step that no longer happens, and a document describing the wrong protocol is worse than no document
- Replace the environment pair with ONE switch, `enabled`, and make it the first key. There are no longer two of anything: one provider, one install token, one address, one deployment. `NODE_ENV: "dev" | "prod"` decided which HALF of a doubled configuration was this process's, which meant the configuration was written twice and the wrong half could be picked silently. What an application actually wants to say is narrower and it is a boolean: is this library holding this application's sessions, or is it not
- AUTHENTICATE at `enabled: false` instead of standing aside, against `di.local_accounts` - a LIST the application lends, never a `signIn` function to write. Comparing, sealing the same cookie with the same password, re-reading the account on every request and filling the session out to the exact shape `/sso/me` answers are this library's work in both states, which is what makes the switch honest: a screen built offline reads `me.profile.city` and `can("read:user")` exactly as it will in production, and the day of the change one line moves. A `signIn` lent instead would be a second login hand-written in each application, and the second always drifts. The application still draws the SCREEN, because a library cannot render its page, and posts to `<basePath>/sso/sign-in`. Lending nothing shuts every door rather than opening them: nobody can sign in there at all, and standing aside served every protected page to whoever asked
- Take the other three addresses from `provider.baseUrl` instead of keeping an address book. The portal comes back with the pairing and the socket is one port further with the path `/realtime` - both facts of x-core's own layout. The login window is NOT: it is that host without its port only where the front has no name of its own, and in production it has one. So it is a last resort that says so in the log, a deployment states `frontUrl` beside `baseUrl`, and x-core answers it in the pairing. The table of hard-coded ecosystems this replaces was a value that outlives the address the day one moves
- Refuse a `baseUrl` that is not an address, at construction, naming it. Carried, it fails much later inside a signature as a `401` that reads like a credential problem, three files from the value that caused it
- STOP THROWING OUT OF `start()`. Every outcome now comes back as `XcoreStartResult` - `withdrawn`, `ready`, `not-paired`, `not-declared` - and is said in one loud line in the log. A boot that died because a token was spent, because the broker was not up yet or because the provider was still starting took the whole application with it, including the pages that have nothing to do with the SSO and including whatever an operator would have used to look at the problem. What is wanted is an application that stands up, says what is not working, and is repaired by a value in a configuration rather than by a container that will not stay alive
- Repeat the provider's OWN WORDS when an install token is refused. Unknown, withdrawn, expired, already redeemed, or still a draft - a form somebody left half finished, with no queue, no broker account and no credential behind it to hand over - are five different repairs, and x-core names which one it is. A message that flattened them into "pairing failed" sent an operator to look at the wrong thing
- SHUT every door until the store says `INSTALLED`, on an application that says it uses the SSO. It used to stand aside, and standing aside is the one thing it must not do: a deployment that never paired then served every protected page to anybody who asked, painted around no account, with the API underneath answering `401` and the page showing zeros. That is not a degraded mode, it is the application with its lock removed at the exact moment nothing can tell one reader from another. `enabled: false` is the opposite case and keeps standing aside: that one is a decision, and what guards the application is its own login
- Read the login window through the store as well, under `SSO_FRONT_URL`, so a provider that starts answering it is followed without a release here
- Fix what `docs/nitro.md` said about hanging the realtime bridge: Nitro has NO runtime hook that hands the server over - `listen` belongs to the build instance and a plugin runs inside the built one. The server behind the first request is what is reachable, and the bridge is hung there once. Written as it was, that line did not compile
- Rebuild `poc/nuxt4-nitro` on the library: its `users` table, its `password_hash` column, its `sessions` table, its login page and its route guard are gone, and the boot drops the two tables on the way through. What is left is an `app_settings` shelf the pairing fills, a `hmac_credential` row the broker fills, and the application's own data. It is the AFTER, kept runnable rather than described, and it is honest about the one thing it needs: without a valid install token it boots, says `not-paired` in one line, and serves nothing behind the SSO
- Take the environment as a KEY, `NODE_ENV: "dev" | "prod"`, stated by the application rather than read from the process. This library reads no `process.env` - that is its rule, and this was the one place breaking it - and read from in here the value would not even be reliable: a bundler (Nitro, Vite, esbuild) replaces `process.env.NODE_ENV` with a constant at build time, so the bundled code carries what was true on the machine that built the image instead of what is true at boot. The application's own line sits in the application's own build, which knows. It is the first key of the object because it decides every other one: which `provider` is called, which `installToken` is presented, and whether this library runs at all
- Refuse anything that is not one of the two literals, at construction, rather than reading it as `dev`. Every failure of this key is otherwise the silent kind: a production process standing down and offering its local login to the internet, a dev machine installing itself into production, or the dev pairing code presented to a production x-core that has never heard of it. All three boot and log their own success
- Track `poc/nuxt4-nitro/.env` rather than a sample of it. The POC is a demonstration stack against a throwaway database, so its values are the ones anybody running it wants and none of them is a secret: a sample to copy was one manual step between cloning the repository and seeing the BEFORE run. The rule stands everywhere else - `.env` remains ignored, and this one path is the single exception
- Publish under `@gestionpratique` rather than `@naskot`. The scope says who owns the thing, and this library is x-core's - it speaks x-core's routes, x-core's HMAC scheme and x-core's catalogue, and runs against nothing else. The two HMAC packages keep their own scope, being general-purpose and owned elsewhere

- Take the ENVIRONMENT out of the configuration and read it from the process. It was a key an operator wrote, which meant one line to change at every deployment - and a deployment that forgot it installed production against the dev provider, silently. `NODE_ENV` decides now, and anything that is not a production build is `dev`: a developer's machine offering to install into production is the wrong default to get wrong
- Make `provider` a pair, one per environment, each naming its API as `baseUrl`. The same configuration ships to both, which is the whole point of reading the environment rather than writing it. `dev` is OPTIONAL and its absence is a decision: without an address there is nowhere to call, so this library stands down in development - no pairing, no declaration, no SSO - and the application keeps whatever local login it has. It does not throw, because a missing key here is how an application says "not in dev"
- Make `installToken` a pair for the same reason, and follow the same switch. A code is minted against ONE x-core and means nothing against the other: it is a row in that database, with that ecosystem's queue, broker account and credential behind it. One field for both meant editing the configuration at every deployment, or installing production with the dev code - which succeeds, silently, and wires the application to the wrong provider
- Replace `di.hmac`'s three closures with TWO FUNCTIONS, and stop receiving the credential store at all. The application used to assemble a signed `fetch`, a header signer and a write, around an object that already exposes all three - so every application recabled the protocol slightly differently, and the imports of `@naskot/node-hmac-auth-core` were in every service file. Now this library names no method of that package: it knows two moments, "give me the current hash" and "store this one", and the application's own line knows how. The day that package renames a method, what breaks is one line in one file rather than this library everywhere at once
- Build the signed transport HERE, from the hash `getCredential` hands back. `signedHttpFetch` and `buildHttpSignedHeaders` are this library's own imports now, so there is still exactly one implementation of the protocol on this side, and it is the one that signs everywhere else in the ecosystem
- STOP WRITING THE PAIRING'S SECRET, which never worked and could not. x-core stores `hashClientSecret(secret, pepper)` and verifies against that; the pepper is its own and never travels. An application that hashed the secret the install answer carries stored something else, signed with it, and collected a `401 BAD_SIGNATURE` on every call while holding the right secret. What signs is the hash x-core computed
- Consume the credential queue IN THIS LIBRARY, with `@naskot/node-hmac-auth-core-propagation` as its own dependency. It is the only side that ever holds what the connection needs - x-core created the queue and the broker account when the code was minted, the nine values come back once in the install answer and the row is deleted in the same breath - and it is the only path by which a usable credential arrives at all. An application writes no AMQP, installs no second package, and adds no environment variable: everything the connection needs came back from the pairing
- Keep the propagation cursor in `environment` rather than asking for a Redis. The propagator wants a Redis-shaped client for the one thing it stores on the receiving path, and requiring a second connection would have been a setting, a dependency and a variable an application did not choose. `HMAC_PROPAGATION_CURSOR` is the nineteenth key, a position rather than a setting, and the only one x-core knows nothing about
- Open the queue BEFORE declaring, so a freshly paired application waits for its credential rather than failing its boot: `declare()` already retries on `NO_CREDENTIAL`, which is exactly the window between redeeming a code and hearing from the broker
- Close the queue with the bridge. A process that exits without letting go leaves a consumer registered until the heartbeat times out, and the next boot finds two

## [Unreleased] - 2026-08-19

- Take the PORTAL's address out of the address book and into the pairing, under `SSO_PORTAL_URL`. One address for three exits, and they are the same exit seen from three sides: a reader who signs out, a session refused because it is over, and a session revoked from somewhere else all land there - the portal being the only thing in this ecosystem that signs a human in. x-core serves it and knows which one an application belongs to, so a constant written down here outlives the address the day it moves, and a sign-out landing on nothing reads as broken rather than as stale. The address book still answers for an application paired before this key existed
- Read that address THROUGH the store rather than capturing it when the middleware is built: the store is read inside `start()`, so a value captured at construction is always the fallback and never what the provider sent
- Name `SSO_PORTAL_URL` in `docs/install.md` as well, where the whole of what `start()` records is listed: a key present in the code and absent from that list reads as one nothing writes
- Add `poc/nuxt4-nitro`, a Nuxt 4 application whose API is Nitro, with the local authentication this library exists to replace: a `users` table, a scrypt password column, a `sessions` table, an `app_session` cookie, a login page and a route guard. It is the BEFORE, kept runnable rather than described, so what the migration removes can be read rather than imagined
- Document that this library replaces the WHOLE local authentication rather than part of it: no user table, no password column, no reset flow, no session table, no permission table, no login page. Worth stating because the reflex is to keep a local session "just in case", and a local session is exactly what cannot honour a revocation - it would still be valid. Nothing is cached here, so a sign-out elsewhere, an account disabled or an access withdrawn lands on the very next call
- Document why there are two environments and why they are not a setting: the four addresses vary per ecosystem rather than per deployment, and the mistake they invite fails silently - the API and the login window differ by a port, and the login window answers `204` to anything it does not know, so an application pointed at it declares itself "successfully" at every boot while nothing exists on the other side
- Rebuild the surface around ONE injection key, `di`, and nothing else. It holds the signed transport, the header signer, the credential write, the application's key/value store and the two push callbacks - and it is short, which is the main fact about this library: it persists nothing. No table, no migration, no schema; an application installing it creates none
- Take the identity, the callback URL, the cancel URL, the template and the gate OUT of the configuration. They are entered on x-core's console when the pairing code is minted, and the pairing brings them back into the application's own store. Writing them in the service made a second source, and it would have won: `declare()` sends what it holds at every boot, so the day the two differed the boot silently replaced what an operator had set - and a callback URL moved that way breaks the login with nothing saying so
- Take the sealing password out too. It is minted at the first boot, kept under `SSO_SESSION_PASSWORD`, and never received from x-core: two applications sharing one could open each other's cookies, while each holds its own revocable session row over there. Deleting the key signs everyone out at once and the next boot mints a new one - a tool, not a fault
- Take the cookie's NAME out as well: it arrives as `SSO_SESSION_COOKIE_NAME`, derived from the identity by x-core. Two applications served under one host would otherwise both write `sso_session` and sign each other out on every navigation, silently, since from each one's point of view the cookie is simply absent
- Replace `install(code)` with the `INSTALLED` key. The pairing code lives in the configuration for the life of the application and what decides is that key, not the code's presence: until it reads true the boot exchanges the code, once it does the boot never looks at it again. Nothing to remove from a configuration afterwards, nothing to remember to call on the right boot, and the state is WRITTEN rather than inferred - the old check looked for a credential in the store, which a propagated one answered "yes" to without any installation behind it
- Write `INSTALLED` in the SAME `save` as everything it announces. Written first, a boot falling between the two would believe itself paired while holding none of it, and would never try again
- Stop signing inside this library. `di.hmac.fetch` and `di.hmac.signHeaders` are handed in, and `@naskot/node-hmac-auth` provides both - the same code that signs everywhere else in the ecosystem, so there is no second implementation of the protocol to drift from the one that verifies in front. No secret ever crosses this library now, and the hash is re-read on every call rather than captured at boot: a client built once would sign with a credential propagation had already replaced
- Drop `bootstrap.elect`. Election belongs to the deployment, which knows what this library cannot: whether there are several workers and how they are numbered. `load()` reads the store on every worker, `start()` pairs and declares on the elected one
- Carry the broker's ADDRESS with the credential it belongs to - `RABBITMQ_PROTOCOL`, `RABBITMQ_HOST`, `RABBITMQ_PORT`. It belongs to the infrastructure and moves with it; an application holding a copy of an old one keeps dialling it long after everybody has moved
- Add the packed tarball under `packages/`, so a consumer installs this library from a path rather than from a registry
- Add `createXcoreBridge`, the single entry point linking an application to the x-core SSO
- Add the pairing service: `install()` sends the pairing code to x-core's dedicated route, unsigned and with no body, and collects what was built when that code was MINTED - the AMQP queue, the broker account, the SSO consumer and the HMAC credential all already exist over there. The secret comes back and is written into the injected credential store; x-core deletes the row and revokes the manager key it borrowed in the same breath. A code minted for another identity is refused rather than adopted: it would install cleanly and then sign as somebody else
- Add the auth service: session opening, token rotation with concurrent-call dedup, account read and permission checks
- Add the sealed session cookie (AES-256-GCM) and its cookie jar over raw Node headers
- Add the framework-agnostic middleware: the five SSO routes, the session guard, the permission guard and the error mapping
- Add the realtime client following each account, so a permission change lands within seconds instead of at the next navigation
- Add the browser WebSocket bridge: single-use tickets, signed upstream handshake, refusal of page-sent `auth` frames and close-code passthrough
- Add the provider address book, written down per environment rather than configured per deployment
- Add `@gestionpratique/node-sso-consumer/client`, the browser half: it reads the session, asks for a ticket, dials this host's socket, reconnects and tells a session that is over from a connection that dropped
- Add `@gestionpratique/node-sso-consumer/express`, imported once for its effect, declaring `req.me` / `req.ssoTokens` / `req.ssoUserId` on the framework's own request type
- Add `live.onAccount` and `live.onSignedOut`, so what the provider pushes reaches a store the library knows nothing about, and `follow()` for a socket of one's own on one account
- Add `bootstrap.elect`, so one worker out of several pairs and declares - the install code is single-use, and a second worker's attempt is refused
- Add `jar()`, the cookie jar of one exchange, for a handler that needs the sealed session rather than the account
- Add the test suite: 107 tests over the sealing, the signed channel, the pairing, the rotation and its dedup, the session, the guards, the tickets and the bridge
- Require the pairing code as `install(code)`'s only argument: it is what the call is about, and one able to run without a code would be a call whose argument reads as decoration. An empty one throws rather than returning `null`, which would read as "already installed". `start(code?)` is the one that falls back on `installToken` in the config, because a boot with no code at all is the ordinary case of every application already installed
- Drop `installToken` from the configuration. `install(code)` is the function for it, and it takes the code as its only argument: a single-use code left in a deployment's configuration outlives the moment it was good for - x-core deletes the row and revokes the manager API key the instant it is spent - so what stayed behind was a dead value sitting among the live secrets. `start(code?)` takes the same code and chains `declare()` onto it, and with no argument it goes looking nowhere: a boot with no code at all is the ordinary case of every application already installed, not a missing setting
- Drop `installQueue` and the whole install body. The queue is named by the infrastructure manager, from the destination and the environment an operator typed on x-core's console, and read back from what it answered - so this library never has an opinion about it, and there is one implementation of the naming rather than two that can disagree. An application still able to send its own callback URL at install would be one able to point somebody else's installation at itself
- Document that this library is proprietary to x-core and runs against nothing else, in the README and at the head of every guide
- Document the package README, the installation guide, the Express, NestJS and Nuxt/Nitro integration guides, and running several processes
