## [0.1.7] - 2026-08-24

- Add `LLM/`, one flat English document written for an agent asked to install this library into an application. The material existed - a README, six guides, nine specifications, four diagrams, in two languages - and that is the problem it solves: nothing said which one is authoritative, so a model traversing them picks a page and invents the rest. They existed because the library had no registry to install from, so a POC pointed at a file path and the packed artefact had to be committed next to the source it was packed from - which means a binary in git that goes stale the moment anything is edited, and two versions of it sitting there proves the point. ## [0.1.2] - 2026-08-23

- Stop hanging up a healthy socket in a background tab. `startHeartbeat` closed anything silent for sixty seconds without asking whether the tab was visible, and a hidden tab has its timers throttled to about one firing a minute - so the check ran at sixty-plus seconds instead of twenty-five, read a silence that had never happened, and killed a perfectly good connection precisely where a pushed change matters most, since a background tab has nothing else that is going to ask. What a consuming application saw was a permission revoked elsewhere moving nothing until somebody focused the tab again, which is the opposite of what holding a socket open is for. The check is gated on `document.visibilityState` now, which is what `specs/05-consuming-realtime.md` has always required
- Reconnect on `online`, `focus` and `visibilitychange`, from inside the client. The spec asks for it and every consuming application had to wire it by hand, so every one of them forgot at least one - and it belongs here anyway: this client is the only thing that knows whether it currently holds a socket. A wake goes STRAIGHT THROUGH the backoff rather than waiting it out, because a reader who has just come back should not sit in front of thirty seconds of rights that may already have been revoked. Free when nothing is wrong: `dial()` returns at once when a socket is open, and the listeners are wired once, on the first `connect()`

- Give the POC store a TYPE COLUMN, `created_at`, and a reader that checks one against the other. `app_settings` was `key`/`value`/`updated_at` with a JSON blob in the middle, and a POC is read as a reference: that shape was copied verbatim into a real application, where it had to be undone. ## [0.1.0] - 2026-08-22

- Write `package-lock.json` for real. It had never been in step with `package.json`: `@naskot/node-hmac-auth-core-propagation` and its `amqplib` were declared as dependencies and never locked, so `npm ci` refused the install outright. Nothing showed it because the publish workflow only runs on a tag and there had never been one - the first tag of this library is what found it, at the first step of its own release
- Add `poc/nuxt4-nest`, where the library runs in a NestJS API the browser never reaches, behind a Nitro relay - the architecture of `manager-infra` and of most of this house's projects, and the one this library had only ever DESCRIBED. `docs/nestjs.md` was prose: nothing had booted it, no test exercised it, and four of the applications waiting to be migrated are Nest. The front half is the proof: `plugins/sso.client.ts`, `composables/useSso.ts` and the pages are the same files as in `poc/nuxt4-nitro`, because the browser only ever talks to its own origin and cannot tell which side of the relay holds the session. What moves is the page guard - under Nitro the library refuses before a byte is written, and here it cannot, because it is not on that side at all, so the console asks over the same relay every other call goes through. Two things break silently in this shape and both are written down where they bite: the callback belongs to the FRONT's address because a browser walks it, and the relay has to SEND `x-forwarded-for` - the library reads it out of the raw headers itself, so without it every session is filed under the relay container's address. `trust proxy` on the API is Express hygiene and nothing this library depends on: it never asks a request what protocol it arrived on, and the cookie's `Secure` comes from the configuration, written by hand. It ships blank - no install token, `not-paired` in one line at boot, and nothing served behind the SSO
- Put `accept` back by hand in the POC's relay, because h3 DROPS IT: the header sits in h3's own `ignoredHeaders` beside `host` and `accept-encoding`, so `getProxyRequestHeaders` never returns it and an API behind a Nitro relay cannot see what the caller asked for. Content negotiation is not degraded there, it is impossible - every refusal took the browser branch, so an XHR on a guarded route was answered with a `302` towards the portal and a `fetch` that follows redirects handed the component the portal's HTML where it expected JSON. It is the exact failure the guides warn about, arriving from the one place nobody looks. Pair the POC against the real x-core to see it: it does not show until a refusal has a portal to name
- Pair `poc/nuxt4-nest` against the production x-core and keep the install token in the file, spent, as `poc/nuxt4-nitro` does. Proven end to end over `https://tvx-gp3.gestionpratique.ovh`: pairing, the twenty keys written into `app_settings` with a sealing password minted locally, the credential hash delivered on the broker queue within the second, a declaration that signs with it and passes on every later boot without re-pairing because `INSTALLED` short-circuits, the authorize redirect with its `Secure` state cookie, both branches of a refusal, a browser sign-in through the portal, and a realtime socket whose `4402` travels back through the reverse proxy and the relay untouched
- Add `poc/nextjs16`, where the library runs in ONE Next.js 16 process - the pages, the six routes and the socket - and the application writes through SERVER ACTIONS rather than through routes of its own. It has no `/api` of its own at all. The App Router cannot host this library directly: its route handlers speak the Web's `Request` and `Response` where the library speaks `IncomingMessage` and `ServerResponse`, and `realtime.attach()` needs an `upgrade` event Next hands to nobody - so a custom server owns the HTTP server and gives Next what is Next's. The session is resolved THERE and carried into the render by `AsyncLocalStorage`, because `sessionOf` re-seals the cookie and writing a cookie is the one thing a Server Component may not do: resolved during a render, every session would break at the first rotation, a quarter of an hour in, silently. A component then reads the account for free - ten of them cost the provider nothing, where an application without a custom server would `fetch` its own `/api/auth/session` once per component. Proven in stand-in mode: the account and its rights rendered server-side out of the store, a Server Action clearing the sealed cookie on the raw response it pulled from the same store, and the same action refused `401` before its own code ran when posted without a session
- Show `permissions.global` in the Next POC's live panel rather than `client.actions()`, and move the count into the client component with it. The two answer different questions - `actions()` filters on the resource THIS application declares and strips its prefix, which on a deployment with no gate returns everything and on one that requires `superadmin` returns six entries with no namespace - and the page was rendering one under a heading that counted the other: `Droits (115)` above a list of 6. Nothing in the library changes; both readings were always right, and only one of them is what the server-rendered first paint had drawn
- Ban the em dash from this repository, 37 of them across ten files, and the three POC in particular: it was reaching the browser in rendered pages. `-` everywhere. The box-drawing rules in comment banners are untouched, being tables rather than punctuation
- Point `exports` at the `.d.cts` declarations under the `require` condition, per subpath. One `types` served both, and since this package is `"type": "module"` TypeScript read that declaration as ESM - so every CommonJS consumer was refused with `TS1479` and could not import this library AT ALL. That is every NestJS project in this house, `nodenext` being what they resolve with, and four of the applications waiting to be migrated are Nest. The `.d.cts` files were built by `tsup` and shipped in the tarball the whole time; nothing pointed at them. Found by booting `docs/nestjs.md` for the first time
- Leave `live` at `false` in that POC rather than copying it on. It follows every account this process holds a session for and hands what arrives to `di.onAccount` and `di.onSignedOut`; neither is lent there, so every one of those sockets carries frames to nowhere - one against x-core per signed-in reader. The realtime a reader actually sees is the ticket bridge, which is untouched by it
- ASK THE PROVIDER ON EVERY READ. `SsoLiveAccounts` no longer answers a guard: it is a relay onto `di.onAccount` and `di.onSignedOut`, and `live.staleAfterMs` is gone with the ceiling it defined. A followed account was served for five minutes between proofs, on the reasoning that a socket which pushes every change cannot go stale - and there is exactly one change it cannot push. A session ended from the portal's sign-ins screen closes NOTHING over there: x-core re-checks a live socket against the IdP session and the account's access, deliberately not against the consumer session row, because that row is replaced at every rotation and pinning a socket to it would close every socket a quarter of an hour in. So the frame never came, and a reader whose session had been revoked kept every door of the consuming application open for five more minutes
- Take what an application REQUIRES from the provider's own answer, `permissions.portail`, and make the door one comparison: `global` holds every entry of `portail`, or the session is over here and the reader goes back to the portal. Both lists speak `resource:action`, so it is a subset test with nothing to parse, split or namespace - and an empty `portail` requires nothing and admits everybody, which is the common case. It was read from what the pairing wrote into the application's own store, and a store is a COPY: an operator adding a requirement on the console changed it over there while every consuming application went on admitting whoever it had admitted the day it was installed. Root needs no exception, being answered the whole catalogue in its `global`. A provider too old to answer the key demands nothing by saying nothing - the only place this parser forgives an absent field, because everywhere else the empty reading is the one that opens a gate
- Read a `403` on the identity read as the access revoked, not as an expiry: `resolve` answers `null` without rotating. Rotating asked the same question twice - the provider checks the access on that path too - and the only thing it bought was a later sign-out
- Put the sign-out on the instance, `xcore.logout(req, res)`, and make it ANSWER where the reader goes rather than redirect there: the portal when this application is paired, its own sign-in screen when the library is standing in. A `302` written into a `fetch` is a response nothing follows - the cookie was cleared and the reader stayed on a page that no longer had a session behind it, until they refreshed by hand. The browser half navigates to what came back
- Kill the realtime bridge while standing in. There is no provider holding that session, so nothing pushes to it: the ticket route answers `404`, which the browser half now tells apart from a `401` - the first means this deployment HAS no stream and the reader is signed in perfectly well, the second means the session is over. Collapsed into "no ticket", it signed everybody out on a deployment that simply has no socket, and the sign-out led back to a page that dialled again, forever
- Subscribe to `me-sessions`, the third always-on topic, and leave a page whose own sign-in disappears from it. That is the ONE way of ending a session `me-signed-out` cannot report: the provider computes it from the IdP session and the account's access, and ending one application's session from the sign-ins screen moves neither - so the frame never came and the page kept painting. Nothing had to be added anywhere: the topic exists, the provider already marks the caller's own line `current`, and this simply listens. Latched on first sight, because a socket with no line to match would read "none is mine" from its first frame and sign everybody out; and settled by ONE read of `/session`, because rotation replaces the row every fifteen minutes and a frame read in the gap shows no line of ours while the session is perfectly alive. This client polls NOTHING - the socket says when something ended, which is what a socket is for
- Refuse through ONE path, whatever the cause. Session over, x-core refusing, x-core unreachable, credential never delivered, never paired: in every one of them nothing was learned about the reader, so the answer cannot differ. To the portal - and `500` when there is no portal to send anybody to, which is an application that never paired, since that address arrives WITH the pairing. `FORBIDDEN` is the one that stays apart, and stays a `403` where the reader stands: the account IS signed in and simply lacks the right, so signing in again would change nothing and loop
- Answer the refusal in the guard rather than handing it to `errors()`. A refusal that depends on an error handler being mounted is one an application can forget to install, and forgetting it did not fail loudly - the request carried on into a framework's default page, which is not a refusal at all
- Throw `NOT_CONFIGURED` from `session()` instead of answering `null` when this library cannot reach the provider. The two are not the same thing and collapsing them was the whole defect: `null` means nobody is signed in, which a caller answers with a `401` and a way to sign in; this means there is no way to sign in at all. Read as the first, every caller said "not signed in" and served the shell of its application to anyone. `statusOf` is the library's own table for turning one into a status, so no application has to work out that a deployment nobody configured must not tell a reader to sign in
- Lend the library `di.errors(refusal, req, res)`. It decides WHETHER and WHY - it is the only thing that talks to the provider, so it is the only thing that can - and calls this from inside that decision to say HOW. The request and response travel with the refusal so one function answers every kind: a `302` written on the response where there is a portal, a throw where the framework stops a handler that way. Optional: lend nothing and the library writes the plain answer itself, and it never writes over a response the application already ended
- Add `account(req, res, ...actions)` for handlers that ASK rather than sit behind a middleware - Nitro, Fastify, a plain route table. The session and the actions are checked in one call and in that order, because two calls are two things to remember and the one that gets forgotten is the first, which is a route asserting rights against an account nobody read
- Default `routes.basePath` to `/api/auth`, not `/auth`. x-core's console COMPOSES the callback it records from the application's address, and it writes that path with no field offering another - so an application configuring nothing was declared at one address and listened at another. It showed up at the first sign-in, as a callback that does not match, on a row whose host is pinned and cannot be edited. Every example in this repository already overrode the old default: a default no document uses is a trap for whoever trusts it
- Drop frames from the page that will not parse, instead of forwarding them. An `auth` frame was already refused - the account behind a socket is decided by the ticket that opened it - and anything unreadable now goes the same way: forwarded, it is a byte string this end never looked at, arriving at the provider over a connection that vouches for this application

It did, and it does not any more: one key installs as many applications as an operator has to install, so it is theirs to keep and theirs to revoke over there. Nothing in this library changes - the pairing answer, the routes and the store keys are untouched - but four documents described a step that no longer happens, and a document describing the wrong protocol is worse than no document

Comparing, sealing the same cookie with the same password, re-reading the account on every request and filling the session out to the exact shape `/sso/me` answers are this library's work in both states, which is what makes the switch honest: a screen built offline reads `me.profile.city` and `can("read:user")` exactly as it will in production, and the day of the change one line moves. The application still draws the SCREEN, because a library cannot render its page, and posts to `<basePath>/sso/sign-in`. So it is a last resort that says so in the log, a deployment states `frontUrl` beside `baseUrl`, and x-core answers it in the pairing. The table of hard-coded ecosystems this replaces was a value that outlives the address the day one moves
- Refuse a `baseUrl` that is not an address, at construction, naming it. Carried, it fails much later inside a signature as a `401` that reads like a credential problem, three files from the value that caused it

- Repeat the provider's OWN WORDS when an install token is refused. Unknown, withdrawn, expired, already redeemed, or still a draft - a form somebody left half finished, with no queue, no broker account and no credential behind it to hand over - are five different repairs, and x-core names which one it is. A message that flattened them into "pairing failed" sent an operator to look at the wrong thing

It used to stand aside, and standing aside is the one thing it must not do: a deployment that never paired then served every protected page to anybody who asked, painted around no account, with the API underneath answering `401` and the page showing zeros. That is not a degraded mode, it is the application with its lock removed at the exact moment nothing can tell one reader from another. `enabled: false` is the opposite case and keeps standing aside: that one is a decision, and what guards the application is its own login

Now this library names no method of that package: it knows two moments, "give me the current hash" and "store this one", and the application's own line knows how. The day that package renames a method, what breaks is one line in one file rather than this library everywhere at once
- Build the signed transport HERE, from the hash `getCredential` hands back. `signedHttpFetch` and `buildHttpSignedHeaders` are this library's own imports now, so there is still exactly one implementation of the protocol on this side, and it is the one that signs everywhere else in the ecosystem
- STOP WRITING THE PAIRING'S SECRET, which never worked and could not. x-core stores `hashClientSecret(secret, pepper)` and verifies against that; the pepper is its own and never travels. An application that hashed the secret the install answer carries stored something else, signed with it, and collected a `401 BAD_SIGNATURE` on every call while holding the right secret. What signs is the hash x-core computed
- Consume the credential queue IN THIS LIBRARY, with `@naskot/node-hmac-auth-core-propagation` as its own dependency. It is the only side that ever holds what the connection needs - x-core created the queue and the broker account when the code was minted, the nine values come back once in the install answer and the row is deleted in the same breath - and it is the only path by which a usable credential arrives at all. An application writes no AMQP, installs no second package, and adds no environment variable: everything the connection needs came back from the pairing
- Keep the propagation cursor in `environment` rather than asking for a Redis. The propagator wants a Redis-shaped client for the one thing it stores on the receiving path, and requiring a second connection would have been a setting, a dependency and a variable an application did not choose. `HMAC_PROPAGATION_CURSOR` is the nineteenth key, a position rather than a setting, and the only one x-core knows nothing about
- Open the queue BEFORE declaring, so a freshly paired application waits for its credential rather than failing its boot: `declare()` already retries on `NO_CREDENTIAL`, which is exactly the window between redeeming a code and hearing from the broker
- Close the queue with the bridge. A process that exits without letting go leaves a consumer registered until the heartbeat times out, and the next boot finds two
