# CHANGELOG

## [Unreleased] - 2026-08-19

- Add `poc/nuxt4-nitro`, a Nuxt 4 application whose API is Nitro, with the local authentication this library exists to replace: a `users` table, a scrypt password column, a `sessions` table, an `app_session` cookie, a login page and a route guard. It is the BEFORE, kept runnable rather than described, so what the migration removes can be read rather than imagined
- Document that this library replaces the WHOLE local authentication rather than part of it: no user table, no password column, no reset flow, no session table, no permission table, no login page. Worth stating because the reflex is to keep a local session "just in case", and a local session is exactly what cannot honour a revocation - it would still be valid. Nothing is cached here, so a sign-out elsewhere, an account disabled or an access withdrawn lands on the very next call
- Document why there are two environments and why they are not a setting: the four addresses vary per ecosystem rather than per deployment, and the mistake they invite fails silently - the API and the login window differ by a port, and the login window answers `204` to anything it does not know, so an application pointed at it declares itself "successfully" at every boot while nothing exists on the other side
- Rebuild the surface around ONE injection key, `di`, and nothing else. It holds the signed transport, the header signer, the credential write, the application's key/value store and the two push callbacks - and it is short, which is the main fact about this library: it persists nothing. No table, no migration, no schema; an application installing it creates none
- Take the identity, the callback URL, the cancel URL, the template and the gate OUT of the configuration. They are entered on x-core's console when the pairing code is minted, and the pairing brings them back into the application's own store. Writing them in the service made a second source, and it would have won: `declare()` sends what it holds at every boot, so the day the two differed the boot silently replaced what an operator had set - and a callback URL moved that way breaks the login with nothing saying so
- Take the sealing password out too. It is minted at the first boot, kept under `SSO_SESSION_PASSWORD`, and never received from x-core: two applications sharing one could open each other's cookies, while each holds its own revocable session row over there. Deleting the key signs everyone out at once and the next boot mints a new one - a tool, not a fault
- Take the cookie's NAME out as well: it arrives as `SSO_SESSION_COOKIE_NAME`, derived from the identity by x-core. Two applications served under one host would otherwise both write `sso_session` and sign each other out on every navigation, silently, since from each one's point of view the cookie is simply absent
- Replace `install(code)` with the `INSTALLED` key. The pairing code lives in the configuration for the life of the application and what decides is that key, not the code's presence: until it reads true the boot exchanges the code, once it does the boot never looks at it again. Nothing to remove from a configuration afterwards, nothing to remember to call on the right boot, and the state is WRITTEN rather than inferred - the old check looked for a credential in the store, which a propagated one answered "yes" to without any installation behind it
- Write `INSTALLED` in the SAME `save` as everything it announces. Written first, a boot falling between the two would believe itself paired while holding none of it, and would never try again
- Stop signing inside this library. `di.hmac.fetch` and `di.hmac.signHeaders` are handed in, and `@naskot/node-hmac-auth` provides both - the same code that signs everywhere else in the ecosystem, so there is no second implementation of the protocol to drift from the one that verifies in front. No secret ever crosses this library now, and the hash is re-read on every call rather than captured at boot: a client built once would sign with a credential propagation had already replaced
- Drop `bootstrap.elect`. Election belongs to the deployment, which knows what this library cannot: whether there are several workers and how they are numbered. `load()` reads the store on every worker, `start()` pairs and declares on the elected one
- Carry the broker's ADDRESS with the credential it belongs to - `RABBITMQ_PROTOCOL`, `RABBITMQ_HOST`, `RABBITMQ_PORT`. It belongs to the infrastructure and moves with it; an application holding a copy of an old one keeps dialling it long after everybody has moved
- Add the packed tarball under `packages/`, so a consumer installs this library from a path rather than from a registry
- Add `createXcoreBridge`, the single entry point linking an application to the x-core SSO
- Add the pairing service: `install()` sends the pairing code to x-core's dedicated route, unsigned and with no body, and collects what was built when that code was MINTED - the AMQP queue, the broker account, the SSO consumer and the HMAC credential all already exist over there. The secret comes back and is written into the injected credential store; x-core deletes the row and revokes the manager key it borrowed in the same breath. A code minted for another identity is refused rather than adopted: it would install cleanly and then sign as somebody else
- Add the auth service: session opening, token rotation with concurrent-call dedup, account read and permission checks
- Add the sealed session cookie (AES-256-GCM) and its cookie jar over raw Node headers
- Add the framework-agnostic middleware: the five SSO routes, the session guard, the permission guard and the error mapping
- Add the realtime client following each account, so a permission change lands within seconds instead of at the next navigation
- Add the browser WebSocket bridge: single-use tickets, signed upstream handshake, refusal of page-sent `auth` frames and close-code passthrough
- Add the provider address book, written down per environment rather than configured per deployment
- Add `@naskot/node-sso-consumer/client`, the browser half: it reads the session, asks for a ticket, dials this host's socket, reconnects and tells a session that is over from a connection that dropped
- Add `@naskot/node-sso-consumer/express`, imported once for its effect, declaring `req.me` / `req.ssoTokens` / `req.ssoUserId` on the framework's own request type
- Add `live.onAccount` and `live.onSignedOut`, so what the provider pushes reaches a store the library knows nothing about, and `follow()` for a socket of one's own on one account
- Add `bootstrap.elect`, so one worker out of several pairs and declares - the install code is single-use, and a second worker's attempt is refused
- Add `jar()`, the cookie jar of one exchange, for a handler that needs the sealed session rather than the account
- Add the test suite: 107 tests over the sealing, the signed channel, the pairing, the rotation and its dedup, the session, the guards, the tickets and the bridge
- Require the pairing code as `install(code)`'s only argument: it is what the call is about, and one able to run without a code would be a call whose argument reads as decoration. An empty one throws rather than returning `null`, which would read as "already installed". `start(code?)` is the one that falls back on `installToken` in the config, because a boot with no code at all is the ordinary case of every application already installed
- Drop `installToken` from the configuration. `install(code)` is the function for it, and it takes the code as its only argument: a single-use code left in a deployment's configuration outlives the moment it was good for - x-core deletes the row and revokes the manager API key the instant it is spent - so what stayed behind was a dead value sitting among the live secrets. `start(code?)` takes the same code and chains `declare()` onto it, and with no argument it goes looking nowhere: a boot with no code at all is the ordinary case of every application already installed, not a missing setting
- Drop `installQueue` and the whole install body. The queue is named by the infrastructure manager, from the destination and the environment an operator typed on x-core's console, and read back from what it answered - so this library never has an opinion about it, and there is one implementation of the naming rather than two that can disagree. An application still able to send its own callback URL at install would be one able to point somebody else's installation at itself
- Document that this library is proprietary to x-core and runs against nothing else, in the README and at the head of every guide
- Document the package README, the installation guide, the Express, NestJS and Nuxt/Nitro integration guides, and running several processes
